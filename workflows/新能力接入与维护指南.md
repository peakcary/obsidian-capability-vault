# 新能力接入与维护指南

## 目的

当 Codex 首次完成一种新任务、接入新工具或形成可复用方法时，用统一流程把它变成可查找、可验证、可持续维护的资产。

“能力”是经过记录和验证的做事方法；“Codex Skill”是从成熟能力中提炼出的可执行包。一次成功先沉淀为能力，不直接宣布为 Skill。

## 什么时候需要接入

满足任一条件时执行本指南：

- 首次使用某个工具、API、模型、文件格式或外部系统。
- 完成了以后可能重复的多步骤任务。
- 解决了复杂故障，并得到可验证的修复方法。
- 形成了重要决策、回退方案或失败经验。
- 用户明确要求保存、复用或制作 Skill。

简单问答、一次性查询、没有复用价值的状态信息不接入。

## 标准接入清单

- [ ] 在 `capabilities/` 搜索名称、触发语句、工具和相近输入，避免重复建卡。
- [ ] 在 `runs/` 记录本次真实执行、结果、产物和验证证据。
- [ ] 新能力使用 [[templates/能力卡模板]] 建卡；已有能力补充本次证据。
- [ ] 明确输入、输出、环境前提、授权边界、执行步骤和验证方法。
- [ ] 记录失败模式、诊断方法和可行回退方案。
- [ ] 把事实、来源、决策和具体项目放入各自目录，并建立双向链接。
- [ ] 更新 `status`、`success_count` 和 `last_verified`。
- [ ] 检查 Frontmatter、内部链接和敏感信息。
- [ ] 完成一批有意义的修改后，通过 Git 提交并同步。

## 内容放置规则

| 内容 | 目录 | 示例 |
| --- | --- | --- |
| 可重复执行的方法 | `capabilities/` | 如何生成并质检讲解音频 |
| 一次真实任务的证据 | `runs/` | 某次模型接入和验证结果 |
| 较完整的操作步骤 | `workflows/` | 图片文博讲解工作流 |
| 已核验事实与概念 | `knowledge/` | 模型参数或领域知识 |
| 事实依据和外部资料 | `sources/` | 官方文档、论文、网页 |
| 技术取舍和理由 | `decisions/` | 为什么选择某模型或架构 |
| 当前具体交付 | `projects/` | 某张图片的讲解项目 |
| 已安装 Skill 的登记 | `skills/` | 路径、版本、验证日期 |

同一段长内容只保留一个权威位置，其他页面用链接引用。

## 成熟度门槛

| 状态 | 必须满足的条件 | 维护动作 |
| --- | --- | --- |
| `idea` | 只有需求或设想 | 补充可验证目标 |
| `draft` | 方法已写出，尚未完整执行 | 完成首次端到端验证 |
| `tested` | 至少一次真实成功，有执行记录 | 继续在不同输入上复用 |
| `stable` | 至少两次独立成功；输入输出、验证、失败模式和回退明确 | 监控工具版本和失效条件 |
| `skill-candidate` | 能力稳定、高频，自动执行价值明确 | 规划 Skill 资源边界 |
| `skill` | Skill 已创建、实际运行并通过验证 | 登记路径、版本和验证日期 |

失败不会自动删除能力。若失败暴露方法缺陷，应记录原因并把状态降回 `draft` 或 `tested`。

## 每次复用后的维护

1. 新增或更新对应执行记录。
2. 成功时增加 `success_count`，更新 `last_verified`。
3. 把新输入类型、新限制和新失败模式合并到能力卡。
4. 工具、模型或 API 版本变化时，重新运行核心验证。
5. 发现能力重复时，保留一个主能力卡，其他页面改为链接。
6. 长期没有验证且依赖已变化时，降低成熟度并标记待复核。

## 晋级为 Codex Skill

能力达到 `skill-candidate` 后才进入 Skill 制作：

1. 用户确认安装位置和作用范围。
2. 使用 `skill-creator` 初始化并组织 `SKILL.md`、脚本、参考资料和资产。
3. Obsidian 保存来源、决策和执行证据；Skill 只保存执行必需内容。
4. 实际运行 Skill，并执行官方验证脚本。
5. 在 [[skills/Skill 索引]] 登记 Skill 路径、版本、状态、验证日期和关联能力卡。

Skill 行为或工具版本改变时，先更新并验证 Skill，再把变化原因和结果回写到 Obsidian。

## 安全边界

不得写入：

- 密码、令牌、SSH 私钥和会话凭据。
- 未经必要处理的私人原始数据。
- 可由工具重新产生的大段日志、缓存和模型文件。
- 没有来源、没有验证却写成确定事实的内容。

需要引用敏感系统时，只记录变量名、存放方式和授权要求，不记录实际值。

## 用户触发语句

完整维护：

```text
把这次任务沉淀到 Obsidian 能力库。先搜索已有能力，创建执行记录并更新能力卡；有重要取舍就记录决策，有可靠资料就记录来源。完成验证后同步 Git，不要保存敏感信息和无价值日志。
```

只做复用检查：

```text
开始前查询 Obsidian 能力库，优先复用已经验证的流程，并说明使用了哪张能力卡。
```

评估 Skill 化：

```text
评估这项能力是否达到 skill-candidate。列出缺少的验证，不要把未成熟能力直接制作成 Skill。
```

## 定期整理

建议每月或积累十次重要执行后检查一次：

- `draft`、`tested` 是否有条件晋级或需要降级。
- `last_verified` 过旧的能力是否依赖已变化。
- 是否存在重复能力、断开的链接和没有证据的结论。
- Skill 登记是否仍对应实际安装路径和当前版本。
- Git 是否已经同步，仓库中是否误入大型文件或敏感信息。
