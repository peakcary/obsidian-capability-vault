# 能力沉淀与复用流程

## 资产类型

| 类型 | 目录 | 回答的问题 |
| --- | --- | --- |
| 能力 | `capabilities/` | 怎样稳定完成一类任务？ |
| 知识 | `knowledge/` | 已核验的事实和概念是什么？ |
| 来源 | `sources/` | 事实和规则依据什么？ |
| 执行记录 | `runs/` | 某次任务实际发生了什么？ |
| 决策 | `decisions/` | 为什么选择这个方案？ |
| 项目 | `projects/` | 当前具体交付是什么？ |
| Skill 登记 | `skills/` | 哪些能力已转成可执行 Skill？ |
| 收件箱 | `inbox/` | 尚未分类的想法和材料是什么？ |

## 完成任务后的沉淀判断

满足任一条件才记录，避免知识库变成流水账：

- 首次接入一个工具、API、模型、文件格式或外部系统。
- 解决了可能再次出现的复杂故障。
- 形成了稳定的多步骤流程或自动化脚本。
- 产生了重要决策、取舍或失败教训。
- 用户明确要求保留、复用或推广该能力。

简单问答、一次性查询、无复用价值的状态信息不记录。

## 沉淀步骤

1. 使用 [[templates/执行记录模板|执行记录模板]] 记录请求、结果、产物、验证和问题。
2. 搜索 `capabilities/` 是否已有对应能力。
3. 已存在：补充新的验证记录、失败模式和最近验证日期。
4. 不存在：使用 [[templates/能力卡模板|能力卡模板]] 创建草稿。
5. 有重要取舍：使用 [[templates/决策记录模板|决策记录模板]] 保存理由。
6. 将执行记录、能力、决策、知识和来源双向链接。
7. 根据晋级条件更新成熟度。

## 成熟度

| 状态 | 条件 |
| --- | --- |
| `idea` | 只有想法，没有执行证据 |
| `draft` | 流程已写出，但未完整验证 |
| `tested` | 至少一次成功执行，有验证结果 |
| `stable` | 至少两次独立成功；输入输出、失败模式和回退方案明确 |
| `skill-candidate` | 稳定且高频，适合做成 Codex Skill；资源边界已规划 |
| `skill` | Skill 已初始化、实现并通过验证脚本 |

失败不会自动降级，但必须记录失败原因。如果失败暴露流程缺陷，应将状态改回 `draft` 或 `tested`。

## 复用流程

1. 根据用户请求搜索 `capabilities/能力索引` 的触发语句、领域和输入。
2. 只加载相关能力卡及它直接链接的知识、来源或脚本。
3. 检查环境前提、授权边界和最近验证日期。
4. 按能力卡执行，不跳过验证步骤。
5. 将本次结果记录到 `runs/`，必要时更新能力。

推荐请求：

```text
开始前先查询 Obsidian 能力库，复用已有流程。
完成后判断本次任务是否产生可复用能力；如果有，创建执行记录并更新能力卡。
不要记录密码、令牌、私人原始数据或无复用价值的日志。
```

## 晋级为 Codex Skill

能力达到 `skill-candidate` 后：

1. 确认 Skill 安装位置。默认可选择 `$CODEX_HOME/skills`，但创建前必须得到用户确认。
2. 使用 `skill-creator` 规划 `SKILL.md`、`scripts/`、`references/` 和 `assets/`。
3. 只把非显而易见、可执行且经过验证的内容放入 Skill。
4. 使用官方 `init_skill.py` 初始化，不手工拼装目录。
5. 实际运行脚本，并使用 `quick_validate.py` 验证 Skill。
6. 将 Skill 路径、版本、验证日期和对应能力卡写入 [[skills/Skill 索引]]。

Obsidian 是能力的来源与审计记录；Codex Skill 是精炼后的执行包。两者不要重复保存大段相同说明。
