# 绿联内嵌播放器部署机制核验

## 请求
分析 NAS 系统，确定播放器在绿联客户端内部窗口打开的部署方法。

## 执行与验证
读取目标系统版本、已安装应用配置、路由和公开运行结构，并对照官方文档。内置漫画应用为 inner，官方 Jellyfin Docker 应用为 tab；独立容器可运行不等于具备内嵌入口。

## 结果
建议复用 Go 核心制作原生 ARM64 UPK，接入 SDK、网关认证、授权目录与应用数据目录。已在项目 docs/ugos-integration-analysis.md 留下设备证据、路线对比、配置草案及验收条件。

## 限制与教训
- 用户反馈无应用开发设置入口。读取目标固件应用中心前端，确认其先查询 GET v1/app/dev-auth，以返回 data.source 是否为真控制 devSetting 标签显示。未读取用户登录会话调用该接口，因此只确认显示条件，未断言具体授权状态。
- 目标固件中文提示支持“个人文件夹已有签名文件后完成整机授权”的官方流程；先获取授权文件，再检查入口，避免循环要求用户寻找条件隐藏的菜单。
- 自制 UPK 安装存在官方开发者授权前提，须先确认整机状态；未发现常规 HOME 中的授权文件不能证明未授权。
- 现有 Basic 认证不等于系统登录，audio 无法直接设置自定义鉴权头，需单独验证 Range 通路。
- shared 以授权软链暴露目录，与网页版拒绝越界软链的规则需明确协调。
- index/player 的嵌套 iframe 不直接符合 SDK 媒体管理层级。
- 不应在未检查正式应用机制前，把 Docker 快捷方式描述成客户端内嵌解决方案。
