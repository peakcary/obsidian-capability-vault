# OlibTauri 的技术架构与业务产品思路

## 核心结论

技术上，学习如何把 Web 界面、原生能力与第三方服务组合成可维护的桌面产品。业务上，学习围绕“找书—获取—管理—阅读”组织完整任务路径，而不是堆积功能。

这是项目学习案例，不是成熟架构认证或市场成功证明。技术观察依据本地代码和验证文档；业务价值判断尚无访谈、留存、收入或实验数据支持。

## 一、值得参考的开发技术

| 技术或设计 | 项目依据 | 可迁移的用途 |
| --- | --- | --- |
| React / TypeScript + Tauri + Rust | src 页面和组件，src/api，src-tauri/src/commands | 用 Web 技术构建界面，将文件、网络、系统操作交给原生后端 |
| 第三方服务集中适配 | src-tauri/src/api.rs、hosts.rs | 隔离认证、协议与线路变化，避免界面散落请求细节 |
| Tokio 异步任务和进度状态 | download.rs 与前端下载队列 | 下载、导入、OCR、转码等长任务 |
| SQLite 本地持久化 | database.rs、download_records.rs，rusqlite 依赖 | 保存历史与应用数据，降低部署复杂度 |
| 内嵌 Axum HTTP 服务 | lan_server.rs、局域网开发文档 | 手机传书、局域网访问和 OPDS；需要另行审查认证与暴露范围 |
| 可选能力插件化 | plugins/，plugin-development.md、ocr.md、format-conversion.md | 按需提供较重能力；不应在无明确需求时提前搭建插件平台 |
| 离线模拟与故障注入 | API 本地 HTTP 测试、下载续验、历史原指令模拟记录 | 稳定复现错误条件，验证难以依赖外部服务重现的行为 |

## 二、最值得学的工程方法

### 1. 围绕变化点划分边界

界面负责交互；命令层衔接桌面调用；客户端负责远端协议；下载管理器负责任务和落盘。界面不直接拼接认证 Cookie，修复请求规则时无需逐页修改。

DRY：共用请求、校验和线路处理。SOLID：保持各模块职责，避免命令层承担所有协议和任务细节。模块独立不意味着必须独立部署成微服务。

### 2. 把长任务当作状态机

任务不仅有成功和失败，还涉及等待、执行、取消与清理。曾出现内层设置 Cancelled 后外层统一错误处理又覆盖成 Failed 的问题，现有修复保留取消状态。

通用检查问题：谁拥有最终状态？取消和失败是否会重复处理？失败后文件如何清理？重试是否安全？并发同名操作怎样协调？

本地测试覆盖部分取消与传输中断场景；无响应下即时取消、并发同名与磁盘写满仍不能宣称解决。

### 3. 先造可控实验，再做真实验收

用环回 HTTP 服务制造 503、响应中断、畸形 JSON；用原指令模拟验证选定历史分支。两者分别回答当前实现行为与原实现局部行为，不能互相替代，更不能代替真实服务验收。

### 4. 保证核心产品可独立维护

历史构建依赖缺失私有模块，限制了 fork 的独立构建。当前用公开兼容客户端补齐核心调用；仍不是恢复原私有源码，也未证明全行为等价。

可迁移经验：外部依赖应有清晰契约，关键构建输入必须可获得，必要时提供可替换实现。

## 三、值得参考的业务思路

| 思路 | 功能体现 | 待验证的业务价值 |
| --- | --- | --- |
| 按用户任务组织功能 | 搜索、详情、下载、收藏、历史 | 缩短从找书到可阅读的路径 |
| 连接既有习惯 | 微信读书、手机传书、外部下载方式 | 降低切换工具和迁移的成本 |
| 减少重复劳动 | 收藏、下载记录、账号切换、书单导入 | 让第二次使用更省事 |
| 从单个内容延伸到集合 | 书单、推荐、相似书籍 | 从明确搜索延伸到阅读发现 |
| 覆盖最后一步 | 转换、OCR、设备传输 | 减少找到资源但仍无法使用的阻塞 |

核心优先级应围绕完成任务：搜索结果是否有用、获取是否成功、文件是否可阅读。更多周边功能不能弥补核心路径频繁失败。这是分析建议，尚非用户数据验证结论。

## 四、风险与取舍

第三方接口、线路、登录和额度会影响体验，但用户通常感知为产品本身失败。可研究的方向包括更准确的错误反馈、可恢复的操作路径、用户自有文件，以及受支持的官方接口。

微信读书元数据、笔记或阅读跳转不等于完整正文获取。历史资料已记录官方 Skills/API Key 路径，但本笔记未重新联网核实现行开放范围，不应据此承诺具体能力。

插件、账号切换、多线路都增加维护成本，应由真实需求决定是否保留。凭据保护、LAN 认证、插件信任仍需独立审查，不把功能存在等同于安全成熟。

## 五、怎样借鉴到自己的产品

| 路线 | 适用场景 | 优势与代价 |
| --- | --- | --- |
| 效率工具，推荐先做 | 明确的单一痛点，如手机传文件到阅读设备 | 价值容易解释，交付范围可控；能力相对集中 |
| 阅读工作台 | 已验证用户需要发现、整理、阅读与输出的一体化流程 | 有持续使用空间；功能和依赖更复杂，需要更多需求验证 |

技术落地先完成“选择输入—执行任务—反馈结果”的最小闭环，再按需要增加存储、网络与插件。KISS/YAGNI：不照搬整个平台；DRY：复用项目已有能力；SOLID：把新增变化放在对应职责边界。

可考虑的产品衡量指标（本项目尚未提供数据）：首次完成任务耗时、核心任务成功率、重复使用率、各步骤退出比例。分析前定义事件、分母、时间窗口和隐私边界，不能将这些指标名称当作已有测量结果。
