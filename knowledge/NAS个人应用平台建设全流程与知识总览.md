# NAS 个人应用平台建设全流程与知识总览

## 这次建立了什么

将家庭 NAS 从文件存储设备扩展为个人应用运行平台：Mac 负责开发和构建，NAS 保存资料并运行应用，云服务器提供 HTTPS 与外网入口，Obsidian 保存可复用方法和验证证据。

本文汇总截至本次会话的实测与文档记录，不是 2026-10-26 的实时在线巡检。配置完成、临时试运行、正式容器运行及重启恢复分别记账，不相互替代。

## 一张图理解整体结构

```text
Mac：代码、构建、测试、SSH 管理
  ├─ 内网 SSH → NAS（ARM64）
  │               ├─ Verse 网页播放器 → 只读音乐目录
  │               ├─ 知识图谱静态站点
  │               └─ frpc 主动建立加密连接
  │                           ↓
  └─ 管理密钥 → 云服务器（AMD64）
                  ├─ frps → 仅回环监听的业务映射端口
                  ├─ Nginx + HTTPS + 站点防护
                  └─ 外网浏览器使用域名访问 NAS 应用

Obsidian：总览 → 能力流程 → 执行证据 → 官方来源与决策
```

## 一、先区分三个目标

| 目标 | 实现条件 | 不能混淆的事 |
| --- | --- | --- |
| 应用在 NAS 运行 | 匹配架构、可运行服务、数据目录与权限 | 桌面程序放入容器不等于能通过网页使用 |
| 从外网访问 | 云服务器、隧道、域名、HTTPS、应用认证 | 配置域名不等于 NAS 服务已启动 |
| 在绿联客户端内部窗口打开 | UGOS 原生应用机制、inner、SDK、网关与开发授权 | Docker 桌面快捷方式可能跳转浏览器 |

## 三、完整推进顺序

### 1. 明确需求与授权范围

先确认访问设备、内网或外网、浏览器或 NAS 客户端内嵌、数据保存在服务器还是浏览器，以及是否需要跨设备同步。先读项目与 Vault 的已有说明，再选择技术路线。

授权用户自己的 NAS 与云服务器，不代表可以收集所有个人文件。只读取任务所需配置；凭证留在用户指定的受限文件，不能写入笔记、日志或代码。

### 2. 网络 → 端口 → 认证 → 权限

NAS 接网线而 Mac 接 Wi-Fi 本身不影响通信；真正需要确认的是 IP、掩码、路由、访客隔离和服务状态。

本次 Mac 最初与 NAS 位于不同网段，切换接入网络后端口可达。不同子网并不必然不可达，但需要有效路由。

- 超时：优先排查网络、防火墙、路由和服务。
- 连接被拒绝：目标可达但服务或端口可能未启用；NAS SSH 到期关闭曾多次出现。
- Permission denied：检查用户、密钥、授权文件与目录权限。

公钥已安装仍被拒绝的一次原因是主目录允许组和其他用户写入；确认权限后修正，认证成功。不能把此修复推广为无条件修改所有 NAS 主目录，需考虑 ACL 和共享用途。

操作方法：[[capabilities/NAS SSH连通与公钥认证排查]]。

### 3. 只读巡检，判断能部署什么

本次设备为 DH4300 Plus、RK3588 八核 ARM64、约 8GB 内存，UGOS 基于 Debian。巡检时负载较低，具备运行轻量服务的余量；该结果不是未来资源保证。

要核对 CPU 架构、应用依赖、磁盘容量、目录权限、现有监听端口及 Docker 权限。只发现阵列成员在线不能说明有镜像冗余：本次仅一块数据盘，仍需独立备份。

### 4. 审查项目，再决定打包方式

| 检查项 | 需要判断的问题 |
| --- | --- |
| 桌面依赖 | Electron/Wails/Tauri 窗口、系统文件选择、原生桥能否在浏览器工作 |
| 服务依赖 | 是否需要数据库、模型、浏览器、API 密钥或外部采集服务 |
| 架构 | 镜像与原生依赖是否支持 ARM64 |
| 数据 | 服务器文件、容器卷、localStorage、离线缓存分别存在哪里 |
| 外部请求 | 是否含原作者统计、广告、第三方 API 或写死的分享域名 |
| 内容与许可 | 保留署名、核对 LICENSE 与实际授权，不能只看 package.json 的许可证字段 |
| 验证入口 | 阅读项目真实测试命令，不能把占位 npm test 当成可用测试 |

### 5A. 桌面应用增加网页模式：Verse

用 build tag 隔离原生 GUI，复用 Go 曲库、歌词和媒体代码。浏览器通过限定 HTTP API 调用后端，以网页目录选择器替换桌面文件对话框。媒体地址改为同源，支持 HTTP Range，以验证真实播放和拖动。

音乐只读挂载，曲库、收藏和下载歌词写入独立数据目录。容器使用普通用户，明确可写目录；声音从浏览器设备输出。

详见 [[capabilities/Wails应用增加无桌面依赖的NAS网页入口]]。

### 5B. 静态应用最小化部署：知识图谱

cn-math-taxonomy 为 HTML/JS/JSON 站点，无需数据库。只打包运行资源与必要数据，排除仓库历史、凭证、截图及生成批次。新增轻量认证静态服务，交叉编译 ARM64，制作 scratch 镜像。

本次同时关闭原作者统计上报、让分享链接跟随实际域名，并保留原作者署名和许可证。孩子档案和答题记录仍保存在浏览器，不会因部署 NAS 自动变成跨设备同步系统。

大 JSON 首次加载与 Service Worker 预缓存竞争上行带宽，曾造成测试等待超时。预压缩后题库传输约为原始的 15%，再测通过；同时验证 gzip、gzip;q=0、正确 MIME、Vary 和离线缓存。

详见 [[capabilities/静态站点部署到ARM64 NAS的准备与验收]]。

### 6. 上传、预览与切换持久容器

本次绿联的 SFTP 路径视图与 SSH shell 不一致，rsync 也受限制，改用 SSH tar 通道上传。不能因一次传输失败就扩大服务端权限。

先校验配置，用受限的临时进程完成目标架构及真实网络测试；临时进程必须有退出策略。准备好镜像、配置和启动命令后，若 sudo 需要交互输入，由用户本机执行，随后继续验收正式容器。

不要让预览进程占用正式容器所需端口。首次构建可以采用已校验的预编译静态程序，减少 NAS 拉取基础镜像和工具链的依赖。

### 7. 接入云服务器与 frp

NAS frpc 主动连接云端 frps；业务映射只绑定云端回环地址，再由 Nginx 提供 HTTPS 域名。使用独立 token 和可验证的隧道证书，应用保留自己的登录认证。

新增系统应新增独立端口、数据目录和 HTTPS 站点，同时检查 frps 的 allowPorts、maxPortsPerClient，以及客户端重建是否会短暂影响其他应用。

本次端口规划：

| 应用或通道 | NAS 端口 | 云端回环映射 | 域名或用途 |
| --- | ---: | ---: | --- |
| Verse | 9866 | 19866 | music.ompeak.com |
| 知识图谱 | 9867 | 19867 | math.ompeak.com，正式容器待验收 |
| frp 控制通道 | 出站连接 | 7000 | 已验证 TLS、令牌与连接路径 |

详见 [[capabilities/通过frp与HTTPS提供NAS应用外网入口]]、[[knowledge/NAS通过云服务器与frp外网访问的架构]]。

### 8. 安全加固与维护

先验证专用管理密钥可独立登录，再限制 root 密码登录，修改后再次连接。不要在新登录方式未验证前关闭旧入口。

音乐站点已实测请求限速、并发限制、登录失败封禁与解封；数学站点复用独立配置并验证封禁动作。封禁作用于具体站点，避免整个云服务器的 HTTPS 端口封禁连带影响其他应用和管理入口。

本次参数为平均 20 请求/秒、突发 80、来源并发 16；10 分钟内 12 次失败封禁 15 分钟。这是当前负载配置，不是所有应用的通用安全常量。

公网证书通过 Certbot 维护；frp 自建隧道证书另有到期时间，需要单独更新。限速与封禁不等于能防所有攻击，单账号密码泄露、应用漏洞和上游 DDoS 仍需分别处理。

详见 [[capabilities/公网个人应用的SSH与登录防护加固]]。

### 9. 按层验收，不只检查端口

| 层级 | 最小验收证据 |
| --- | --- |
| 构建 | 匹配架构，配置与必要代码检查通过 |
| 内网服务 | 未登录拒绝、正确登录成功、核心页面或 API 可用 |
| 文件访问 | 媒体范围受限、私密路径与目录列表拒绝、写入目录正确 |
| 容器 | 普通用户、挂载属性正确、实际进程可用 |
| 隧道 | 控制认证成功、代理注册、回环映射可达 |
| HTTPS | 公网证书有效、域名匹配、应用鉴权有效 |
| 业务 | 真实音频播放与 Range，或图谱/诊断/档案操作 |
| 性能与离线 | 首次加载、压缩、移动布局、Service Worker 缓存与更新 |
| 防护 | 限流、封禁、解封、正常访问恢复；移除测试规则 |
| 生命周期 | 正式容器启动、重连、应用和主机重启后恢复；未测就明确标注 |

## 四、最重要的知识区别

| 容易混淆 | 正确理解 |
| --- | --- |
| NAS 密码、应用密码、frp token | 三种不同凭证；专用 SSH 私钥又是另一种管理凭证 |
| HTTPS 与 frp TLS | 浏览器到云端、云端到 NAS 是两段链路；公网证书与隧道证书分别维护 |
| 加密与鉴权 | 加密不自动验证服务器身份，隧道认证不自动验证网页用户 |
| 网页可用与客户端内嵌 | frp 和 Docker 不自动提供 UGOS inner 应用能力 |
| NAS 存储与浏览器存储 | 音乐在 NAS；知识图谱档案在 localStorage；备份覆盖范围不同 |
| RAID、同步与备份 | 冗余、文件一致和可恢复副本不是同一件事 |
| HTTP 可达与浏览器可达 | 浏览器有代理、权限和缓存等独立条件；Chrome 局域网权限原因本次未最终证实 |
| 声明支持某扩展名与可播放 | 编解码能力由客户端决定，未部署转码不能保证所有音频格式可播 |

## 五、绿联客户端内嵌路线的前提

实查设备配置：内置漫画应用采用 inner，Jellyfin 采用 tab。官方原生机制还要求 SDK、系统网关认证、独立应用用户、数据目录和共享目录授权。

用户找不到“应用开发设置”后，读取应用中心前端代码发现它根据开发授权响应 source 字段条件显示。没有入口与未识别授权来源一致，但仅凭 UI 不能断定具体授权状态。官方流程是先申请设备开发授权文件，再按固件流程完成整机授权。

音频自定义鉴权头、Range、授权软链接以及播放器多层 iframe 与媒体 SDK 的兼容性尚未实现和验收。当前推荐原生 ARM64 UPK 是方案决策，不是已交付功能。

详见 [[knowledge/绿联NAS部署播放器与客户端内嵌应用知识总结]]、[[decisions/绿联客户端内播放器采用原生UPK适配路线]]。

## 六、已知问题与失败教训

- 不要先承诺快捷方式能内嵌，之后才发现打开方式与授权门槛。
- 根目录权限与 ACL、公钥位置都可能影响 SSH；先取得证据，再最小修正。
- Go 平台标签要合并，Objective-C 文件也需隔离；重复 go:build 会直接失败。
- iframe 内控件调用父页面绑定时，弹窗可能出现在父文档；UI 测试要定位正确。
- 不能把 GitHub 默认账号无权访问误判为仓库不存在；本次复用专用 SSH 账号读取私有仓库。
- 不要用固定短等待判断大 JSON 初始化失败，先检查响应、下载量、缓存和首次网络开销。
- 知识图谱的引擎测试为 88 通过、1 失败：预期数学点数 828，实际 827。保持该既有问题可见，未为部署而改测试或题库。
- 技术测试通过不代表 AI 生成的教学数据经过教师审核，也不表示商业授权成立。
