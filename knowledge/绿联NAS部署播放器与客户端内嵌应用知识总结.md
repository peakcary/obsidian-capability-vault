# 绿联 NAS 部署播放器与客户端内嵌应用知识总结

## 核心结论

在 NAS 上运行程序、添加桌面图标、在绿联客户端内部打开，是三个不同的交付目标。开始部署前先确认用户要的是哪一个，避免只完成 Docker 部署却声称实现客户端内嵌。

| 目标 | 实现方式 | 本次状态 |
| --- | --- | --- |
| Mac 播放 NAS 音乐 | 桌面播放器访问 NAS 文件共享 | 可选路线，未作为本次交付验收 |
| 浏览器播放 NAS 音乐 | NAS 运行网页服务或 Docker 容器 | 已部署并完成真实音乐播放验证 |
| 绿联桌面显示图标 | 为容器添加桌面快捷方式 | 用户实测点击后跳转 Mac 浏览器 |
| 绿联客户端内部播放 | 接入 UGOS 应用机制，配置 inner 并完成认证与媒体适配 | 方案已核验，原生应用尚未实现和安装 |

当前建议：保留已验证的网页运行模式，新增原生 ARM64 UPK 模式以实现客户端内嵌。此建议记录于 [[decisions/绿联客户端内播放器采用原生UPK适配路线]]。

## 一、先解决网络，再解决 SSH 认证

- NAS 接网线、Mac 接 Wi-Fi 可以互通；应核对实际 IP、掩码、路由及访客隔离，而不是只看连接介质。
- 不同子网不一定不可达，但必须存在有效的双向路由。本次切换 Mac 接入网络后，NAS 网页和 SSH 端口恢复可达。
- SSH 连接超时优先检查网络、端口及服务状态；认证失败则继续检查账号、公钥和权限。
- NAS 的 SSH 可能设置自动关闭，到期后应检查是否重新启用并应用配置。
- UGREENlink 网页入口不能直接作为 SSH 主机地址。

常用只读诊断命令，地址与用户名均使用自己的实际值：

```sh
networksetup -getinfo Wi-Fi
route -n get <NAS_IP>
nc -vz -G 3 <NAS_IP> 22
ssh <用户名>@<NAS_IP>
```

本次公钥已正确写入，但用户主目录允许其他用户写入，SSH 因权限检查拒绝公钥。修正主目录写权限后成功登录。`.ssh` 常用权限为 700，`authorized_keys` 为 600；还需核对属主及 ACL，不能盲目递归修改共享目录。

完整方法与证据：[[capabilities/NAS SSH连通与公钥认证排查]]、[[runs/2026-10-25-NAS SSH连接与只读巡检]]。

## 二、桌面播放器不能直接等同于 NAS 网页服务

本次项目 Verse 听页基于 Go 与 Wails，桌面窗口、文件选择和前端绑定依赖桌面环境。Docker 化前先增加无 GUI 网页入口，复用曲库、歌词与音频逻辑。

已验证的改造方式：

1. 用 Go build tag 分离桌面与网页入口，保留桌面版回归。
2. 将 Wails 调用适配为受限的 HTTP API，用 NAS 目录选择器替代系统文件对话框。
3. 将本机回环音频地址转换为网页同源地址，支持 HTTP Range，保证进度跳转。
4. 音乐目录只读挂载；曲库、收藏和下载歌词保存在独立数据目录。
5. 针对 ARM64 交叉编译静态 Go 程序。可将程序与公开 CA 证书组成 scratch 镜像，避免在 NAS 上下载完整构建环境。
6. 普通用户运行容器；Docker 启动若要求 sudo，由用户在本机交互输入密码。

声音由访问网页的 Mac 或手机播放，并非 NAS 自己输出。支持的音频扩展名也不等于浏览器能解码所有编码；当前没有服务端转码。

验证覆盖实际容器登录、真实音乐播放、Range、歌词接口、刷新恢复和移动端目录选择；已确认普通用户运行、音乐只读及曲库文件保存，未执行容器重启验收。

完整方法：[[capabilities/Wails应用增加无桌面依赖的NAS网页入口]]；执行证据：[[runs/2026-10-25-Wails播放器增加NAS网页模式]]。

## 三、UGOS 内嵌应用需要的系统集成

官方区分两种打开方式：`inner` 是系统桌面内窗口，`tab` 是浏览器新标签页。本次实际检查发现，内置漫画应用为 inner，应用中心安装的 Jellyfin 为 tab。因此“安装在应用中心”也不保证在客户端内部打开。

推荐的原生结构：

```text
绿联客户端内嵌窗口
  → UGOS 静态资源与认证网关
  → Verse 原生 Go 后端
  → 用户授权的音乐目录 + 应用独立数据目录
```

需要适配的要点：

| 部分 | 要求与边界 |
| --- | --- |
| 应用入口 | ARM64、nasync UPK，配置 open_type: inner |
| 前端与后端 | 静态文件和原生服务分别打包，由系统管理路由与生命周期 |
| 登录 | SDK 获取第三方 token；系统网关校验并向后端注入用户信息，不能直接信任外部可伪造的请求头 |
| API 与媒体 | 请求都应纳入已配置的代理通路；HTML audio 无法像 fetch 一样直接设置自定义鉴权头，音频认证及 Range 尚待验证 |
| 音乐授权 | 开启 allow_add_access_path；用户授权目录由 UGAPP_SHARED_DIR 暴露，需正确处理其授权软链接 |
| 数据目录 | 使用 UGAPP_DATA_DIR，而非假定可访问 Docker 的旧数据目录 |
| 网络能力 | 歌词匹配需声明 NETWORK.ACCESS_INTERNET |
| 媒体窗口 | 官方 mediaCenter 不支持多层嵌套 iframe，需调整当前页面层级或注册方式 |

最终需在绿联客户端验收内嵌打开、播放、跳转、登录过期、窗口关闭及目录授权撤回。现阶段仅完成方案核验，不能把网页测试结果当作原生应用已验收。

## 四、没有“应用开发设置”入口的原因与流程

本次读取目标固件的应用中心前端代码，确认设置页会先查询 `GET v1/app/dev-auth`，仅在返回数据存在有效来源标记 `source` 时显示开发设置标签。

这证明入口是条件显示。没有入口与系统尚未识别开发授权来源一致，但本次没有调用用户登录会话下的该接口，不能据此断言具体授权状态。

官方顺序是：

1. 联系绿联申请测试设备开发者授权。
2. 按官方要求直接向绿联提供设备序列号、MAC 和管理员用户名。
3. 取得授权文件，重命名为 `ugdev.sig`，放入管理员个人文件夹。
4. 在对应固件要求的应用中心设置中完成整机授权；文件安装后仍无入口，应向绿联确认型号、版本及授权状态。
5. 使用官方 ugcli 在 Linux 打包正确架构与产品线的 UPK，再通过应用中心手动安装。

不要循环让用户寻找尚未满足显示条件的菜单，也不要仅因菜单不存在就断言固件版本过低。

### 开发者申请邮件要点

用户提供的官方模板要求标题形如：`【绿联云开发者申请】应用名_开发主体名称`。

正文包含套件名称、个人或企业主体、主体名称、主要功能、联系人与联系方式。申请测试授权时另补充设备型号、系统版本、架构、管理员用户名及官方要求的设备标识，并明确说明申请“客户端内嵌应用测试授权”。

设备标识、联系方式及授权文件由用户直接提交绿联；本笔记不保存真实值。申请邮件草稿不代表已提交、审核或获得授权。

## 五、本次踩坑与验证纪律

- **把快捷方式误认为内嵌应用**：必须先核对实际打开方式和官方应用机制。
- **只测命令行就断定用户浏览器可用**：直接 HTTP、浏览器、客户端 WebView 是不同访问环境。出现 ERR_ADDRESS_UNREACHABLE 时，分别检查系统局域网权限与代理；本次 Chrome 权限原因尚未最终证实。
- **忽略构建约束**：新增 build tag 要合并原平台表达式，Objective-C 文件也要处理，否则编译失败。
- **文件传输路径不同**：本次 SFTP 和 SSH shell 可见目录不同，rsync 受限制，使用 SSH tar 通道完成上传。
- **单盘 RAID1 不等于镜像冗余**：阵列成员在线只能说明当前配置的成员状态，不能证明有第二块盘保护数据。
- **区分验证层级**：原生二进制运行、Docker 运行、浏览器播放、绿联客户端内嵌播放需分别记录结果。
